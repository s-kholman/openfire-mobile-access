# Openfire: MAM и офлайн-сообщения без дубликатов

## Проверенная конфигурация

- Openfire 5.1.1
- Monitoring Service 2.8.0
- Conversations
- MAM включён
- Архивирование личных сообщений включено
- `xmpp.offline.type = drop`

## Симптом

Когда получатель находился офлайн, после повторного подключения последнее личное сообщение появлялось дважды.

Проверка XML Debugger показала, что Openfire действительно отправлял клиенту две копии одного сообщения:

1. сначала как результат запроса MAM;
2. затем как обычное офлайн-сообщение из Offline Message Store.

Обе копии содержали одинаковый `message id`.

В базе данных при этом находилось:

- одна запись в `ofMessageArchive`;
- одна запись в `ofOffline`.

Таким образом, дублирование возникало не из-за повторной записи сообщения, а из-за одновременной доставки двумя независимыми механизмами: MAM и Offline Message Store.

## Рабочее решение без дополнительного плагина

Offline Message Store переведён в режим `drop`:

```text
xmpp.offline.type = drop
```

В интерфейсе Openfire этому соответствует:

```text
Server Settings → Offline Messages → Delete
```

В русской локализации:

```text
Настройки сервера → Офлайн-сообщения → Удалять
```

Описание варианта:

> Никогда не хранить недоставленные сообщения и удалять их без уведомления отправителя.

Пример изменения напрямую в PostgreSQL:

```sql
UPDATE ofProperty
SET propValue = 'drop'
WHERE name = 'xmpp.offline.type';
```

После изменения требуется перезапуск Openfire:

```bash
sudo systemctl restart openfire
```

Проверка текущего значения:

```sql
SELECT name, propValue
FROM ofProperty
WHERE name = 'xmpp.offline.type';
```

Ожидаемый результат:

```text
xmpp.offline.type | drop
```

## Результат проверки

После переключения на `drop`:

- дубликаты исчезли;
- сообщения, отправленные пользователю офлайн, загружаются после входа через MAM;
- порядок сообщений сохраняется;
- история чата повторно загружается с сервера после удаления локальной истории в Conversations;
- новые записи в `ofOffline` для этой схемы не требуются.

Фактически MAM становится единственным источником истории сообщений.

## Важное ограничение

Режим `drop` подходит только тогда, когда используемые клиенты поддерживают MAM.

Клиенты без поддержки MAM не смогут получить сообщения, отправленные им во время отсутствия, поскольку Offline Message Store их больше не сохраняет.

Кроме того, Monitoring Service и архивирование личных сообщений должны оставаться включёнными. Если MAM будет отключён или Monitoring Service перестанет работать, офлайн-сообщения в режиме `drop` восстановить будет невозможно.

## Связанный дефект

Похожая проблема зарегистрирована в Monitoring Plugin:

- `igniterealtime/openfire-monitoring-plugin#391` — Duplicated one-on-one messages

Найденная настройка является рабочим серверным обходным решением, но не исправлением исходного дефекта Monitoring Service.
