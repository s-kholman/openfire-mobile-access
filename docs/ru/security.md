# Модель безопасности

## Цели безопасности

- Компрометация мобильного устройства не должна раскрывать пароль Active Directory.
- После перехода на итоговую конфигурацию Openfire не должен принимать LDAP-пароли.
- Мобильный доступ выдаётся и отзывается независимо от пароля AD.
- Локальные мобильные учётные данные нельзя создать для пользователя, отсутствующего в LDAP.
- Все административные действия должны быть однозначно связаны с инициатором и доступны для аудита.

## Границы доверия

1. Active Directory и LDAPS являются источником истины для идентичности сотрудников и членства в группах.
2. Kerberos является источником истины для доменного SSO на Windows.
3. PostgreSQL Openfire хранит данные проверки локального мобильного пароля.
4. Административная страница плагина доступна только администраторам Openfire.
5. Мобильные клиенты считаются недоверенными конечными устройствами.

## Обязательные меры защиты

### Проверка LDAP

Перед любой записью учётных данных плагин должен:

- выполнить свежий LDAP-запрос;
- получить ровно одного пользователя;
- сравнить `sAMAccountName` с запрошенным логином;
- проверить членство в разрешённой группе;
- запретить операцию при ошибке LDAP или неоднозначном результате.

### Работа с паролями

- использовать поля ввода с маскировкой;
- требовать повторный ввод для вручную заданного пароля;
- применять настраиваемую минимальную длину;
- никогда не журналировать пароль;
- не возвращать пароль после завершения ответа, в котором он был создан;
- по возможности очищать временные массивы символов;
- использовать штатный API Openfire вместо собственной реализации хеширования.

### Запись в базу данных

- использовать подготовленные выражения;
- изменять только необходимые парольные столбцы;
- не копировать LDAP-профиль в локальную строку без технической необходимости;
- применять транзакции для многошаговых операций;
- сделать повторные операции выдачи и отзыва идемпотентными.

### Защита административного интерфейса

- проверять права администратора Openfire;
- выполнять изменения только методом POST;
- использовать защиту от CSRF;
- валидировать данные на сервере;
- экранировать вывод в JSP;
- не передавать чувствительные значения в URL.

### Аудит

Событие аудита содержит:

- дату и время;
- логин или JID администратора;
- логин целевого пользователя;
- действие;
- результат;
- удалённый IP-адрес;
- нечувствительную причину ошибки.

В аудит запрещено записывать пароли, SCRAM-ключи, соли и полные данные сервисной LDAP-учётной записи.

## Семантика отзыва доступа

Отзыв очищает только локальные мобильные парольные данные. Он не должен:

- удалять LDAP-пользователя;
- изменять Active Directory;
- удалять LDAP-группы;
- нарушать Kerberos/GSSAPI-аутентификацию.

При необходимости после отзыва могут завершаться активные XMPP-сессии. Такое поведение должно быть явно настроено и протестировано.

## Политика отказа

Плагин запрещает операцию, если:

- LDAP недоступен;
- невозможно подтвердить разрешённую группу;
- найдено более одной LDAP-записи;
- логин содержит домен или JID в неподдерживаемом формате;
- транзакция базы данных завершилась ошибкой;
- текущая конфигурация провайдеров Openfire несовместима с работой плагина.

## Политика развёртывания

Первая установка выполняется только на тестовом Openfire. До установки необходимо:

- сохранить резервную копию `openfire.xml`;
- создать дамп PostgreSQL;
- проверить рабочий аварийный вход администратора;
- подготовить инструкцию отката;
- протестировать работу на одной учётной записи `s_kholman`.
