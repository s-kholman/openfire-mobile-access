# Архитектура

## Общая схема

Плагин добавляет административный механизм управления локальными мобильными паролями, при этом Openfire продолжает получать данные сотрудников из Active Directory.

```text
Windows Spark
    -> SASL GSSAPI / Kerberos
    -> Openfire
    -> данные пользователя из LDAP

Мобильный XMPP-клиент
    -> парольный механизм SASL
    -> DefaultAuthProvider
    -> локальные парольные данные в ofUser
    -> данные пользователя из LDAP
```

Оба способа входа используют одинаковый логин и один JID.

## Модель провайдеров

Целевая конфигурация Openfire:

```text
User Provider:   LDAP, при необходимости через HybridUserProvider для аварийного локального администратора
Group Provider:  LDAP
VCard Provider:  LDAP
Auth Provider:   DefaultAuthProvider
Kerberos:        SASL GSSAPI, настраивается отдельно от AuthProvider
```

`LdapAuthProvider` не должен присутствовать в итоговой цепочке аутентификации.

## Основные компоненты

### MobileAccessPlugin

Точка входа жизненного цикла плагина Openfire. Инициализирует сервисы, схему базы данных и интеграцию с административной консолью.

### LdapIdentityService

Проверяет:

- существование LDAP-записи;
- точное совпадение `sAMAccountName` с нормализованным логином;
- членство в настроенной группе мобильного доступа;
- соответствие учётной записи дополнительным правилам доступа.

Сервис не проверяет пароль AD.

### MobileCredentialService

Координирует создание, замену и отзыв мобильных учётных данных. После завершения операции пароль не должен оставаться доступным.

### CredentialRepository

Выполняет строго ограниченные операции с контейнером локальных парольных данных. Не должен перезаписывать LDAP-атрибуты профиля, например имя или email.

### AuditService

Записывает административные действия, результат, инициатора, целевого пользователя и удалённый адрес. Пароли и производные от них значения не журналируются.

### Административный веб-слой

Добавляет страницы в консоль Openfire с проверкой прав администратора и защитой от CSRF.

## Стратегия хранения учётных данных

`DefaultAuthProvider` Openfire хранит данные проверки пароля в таблице `ofUser`. LDAP остаётся единственным источником профиля пользователя.

Для LDAP-пользователя плагин может создать минимальную теневую строку с тем же username. Эта строка предназначена только для локальных парольных данных.

Перед включением операций записи необходимо подтвердить точный контракт базы данных Openfire 5.1.1. Самостоятельное формирование хешей не используется, если доступен безопасный штатный API Openfire.

## Правила логина

Разрешено:

```text
s_kholman
```

Запрещено:

```text
KRIMM\\s_kholman
s_kholman@krimm.local
s_kholman@openfire.krimm.ru
```

Нормализованный логин должен строго совпадать с LDAP-атрибутом `sAMAccountName` с учётом настроенной политики регистра.

## Аварийный локальный администратор

Полностью локальный аварийный администратор является отдельной задачей. При необходимости он подключается через `HybridUserProvider`, где LDAP используется как основной провайдер, а `DefaultUserProvider` — как дополнительный.

Функция мобильных учётных данных сотрудников никогда не должна создавать произвольные локальные личности, отсутствующие в LDAP.

## Возможные расширения

- самостоятельная смена пароля;
- короткоживущие токены регистрации;
- настройка через QR-код;
- второй фактор;
- интеграция с Laravel;
- срок действия мобильного доступа;
- политика доступа по устройствам.
